🔴 Incidente Reportado

Diretor de Vendas: "Estou tentando gerar o relatório de vendas diárias do cliente X, mas a tela fica em 'loading' infinito e nada acontece."
Root cause identificado: Edge Function no Supabase retornando HTTP 504 Gateway Timeout ao tentar comunicar com a API do Open Finance do cliente.

01 Análise Crítica — Por que o setInterval é perigoso? ⚠ ANTI-PATTERN

Sugestão do Júnior: polling a cada 2s no frontend até a API responder.

❌ O que acontece na prática
  • Cada usuário abre N conexões simultâneas à Edge Function
  • Edge Functions têm cold-start e limite de invocações/minuto
  • Com 50 usuários × 30 chamadas/min = 1.500 req/min → throttle / ban
  • Se a API de Open Finance estiver lenta, o problema se amplifica
  • Race conditions: 2 respostas chegam fora de ordem
  • Usuário fecha a aba → interval continua rodando (memory leak)
  • Sem backoff → DDoS acidental na API de terceiro
  • UX péssima: spinner eterno, sem feedback de progresso
✅ O que queremos alcançar
  • Fluxo assíncrono: dispara e libera o usuário
  • Feedback de progresso real (não spinner cego)
  • Retries com backoff exponencial no lado servidor
  • Idempotência: mesma requisição não duplica dados
  • Custo de infra previsível e controlado
  • Observabilidade: log de cada tentativa
  • Resiliência: circuit breaker se a API cair
// ❌ Sugestão do Júnior — o que NÃO fazer const interval = setInterval(async () => { const res = await supabase.functions.invoke('gerar-relatorio', { body: { clienteId } }); if (res.data?.done) clearInterval(interval); }, 2000); // dispara a cada 2s SEM LIMITE, SEM BACKOFF, SEM CLEANUP
⚡ Regra de ouro: nunca deixe o frontend controlar o ritmo de operações de longa duração em APIs de terceiros.
02 Troubleshooting — Passos para debugar o root cause 🔍 DEBUG
🪵
1. Checar Logs da Edge Function no Supabase Dashboard
Dashboard → Edge Functions → Logs.
O que procurar: tempo de execução, stack trace, mensagem exata do timeout, qual endpoint da Open Finance foi chamado.
Confirmar se o 504 é do Supabase ou da API de terceiro (header x-cache, cf-ray).
⏱️
2. Medir tempo real da chamada à Open Finance API
Adicionar console.time / console.timeEnd ou timestamp manual antes e depois do fetch.
Edge Functions Supabase têm timeout padrão de ~60s. Se a API demora 70s → 504 garantido.
Testar isoladamente via curl/Postman direto na URL da Open Finance para medir latência sem overhead do Supabase.
🌐
3. Verificar rede / firewall / allowlist da Edge Function
Edge Functions rodam em ambiente isolado (Deno). Confirmar que o domínio da Open Finance está liberado no egress.
Alguns providers de Open Finance exigem IP fixo em allowlist — verificar se o IP do Supabase está cadastrado.
📊
4. Analisar volume de dados retornado
A API pode retornar JSON muito grande (transações do mês inteiro) e o parse está sendo lento.
Verificar se existe paginação disponível na API e se não estamos buscando tudo de uma vez.
🔁
5. Checar status e SLA da Open Finance API
Verificar statuspage do provedor. Confirmar se é problema pontual (fora do ar) ou sistêmico (API lenta por design).
Decisão de arquitetura muda dependendo da resposta.
03 Arquitetura — Solução correta: Jobs Assíncronos ⚙ ARCHITECTURE

Padrão: Fire-and-forget + Job Queue + Polling/Realtime via Supabase

1️⃣
Frontend dispara e recebe job_id imediatamente
React chama a Edge Function Dispatcher que cria um registro na tabela relatorio_jobs com status 'pending' e retorna o job_id em <200ms.
UI mostra: "Seu relatório está sendo gerado, avisaremos quando pronto." — usuário fica livre.
2️⃣
Worker processa o job em background (com retries + backoff)
Supabase pg_cron ou uma 2ª Edge Function processa jobs pendentes.
Retry com backoff exponencial: 5s → 15s → 45s → 2min → desiste e marca como 'failed'.
Timeout do worker configurado para 300s (independente do timeout padrão da Edge Fn de 60s).
3️⃣
Supabase Realtime notifica o React quando pronto
React faz subscribe no canal Supabase Realtime para o job_id específico.
Quando o worker atualiza status para 'done', o React recebe o evento e exibe o relatório.
Zero polling. Zero setInterval. Zero carga desnecessária.
// ✅ Edge Fn: Dispatcher (retorna rápido) export default async handler(req) { const { clienteId } = await req.json(); const { data: job } = await supabase .from('relatorio_jobs') .insert({ cliente_id: clienteId, status: 'pending' }) .select() .single(); return Response.json({ jobId: job.id }); // retorna em ~50ms } // ✅ React: subscribe via Realtime (sem polling) const channel = supabase .channel(`job-${jobId}`) .on('postgres_changes', { event: 'UPDATE', schema: 'public', table: 'relatorio_jobs', filter: `id=eq.${jobId}` }, (payload) => { if (payload.new.status === 'done') mostrarRelatorio(payload.new.resultado); if (payload.new.status === 'failed') mostrarErro(); }) .subscribe();

Título [BUG] Relatório de Vendas trava em loading infinito — Edge Function 504 Timeout
Reporter Diretor de Vendas · Assignee: Dev Sênior
📝 Descrição / Contexto
Ao tentar gerar o relatório de vendas diárias do Cliente X, a tela permanece em loading infinito. Investigação revelou que a Edge Function no Supabase retorna 504 ao chamar a API do Open Finance, pois a latência da API terceira excede o timeout da função (60s).
🔍 Root Cause
  • API Open Finance com latência média de 80-120s (acima do timeout de 60s da Edge Fn)
  • Arquitetura síncrona: React esperava resposta direta da Edge Function
  • Sem mecanismo de retry ou fallback no servidor
✅ Solução Implementada
  • Refatoração para arquitetura assíncrona: Job Queue via tabela relatorio_jobs no Supabase
  • Edge Fn Dispatcher retorna job_id em <200ms
  • Worker com retry exponencial processa em background
  • Supabase Realtime notifica o frontend quando o job é concluído
  • Botão com debounce para prevenir jobs duplicados
